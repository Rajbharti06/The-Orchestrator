# Testing Rules — Always Follow

These rules apply to all test code generated by the orchestrator.

## Coverage Requirements

| Layer | Minimum |
|-------|---------|
| Unit tests | 80% line coverage |
| Branch coverage | 70% |
| Integration tests | All happy paths + top 3 error paths |
| E2E tests | All user-facing flows |

Never ship code that doesn't meet these thresholds.

## Test-First Rules

- Write failing tests BEFORE implementing the feature
- Tests are part of the definition of done — feature is not done until tests pass
- No commenting out failing tests to make CI pass

## Test Quality Rules

### Structure (AAA Pattern)
```javascript
it('should describe the behavior, not the implementation', async () => {
  // Arrange — set up data and dependencies
  // Act — call the thing being tested
  // Assert — verify the outcome
});
```

### Naming
- Test names describe behavior: `should return 401 when token is expired`
- NOT: `test auth`, `test1`, `authTest`
- Group with `describe('ComponentName.methodName')`

### One Assertion Per Test
- Each test verifies one thing
- Multiple assertions in one test hide which assertion failed
- Exception: property assertions on the same object

### Test Independence
- Tests never depend on execution order
- No shared mutable state between tests
- Each test can run in isolation
- `beforeEach` resets state; `afterEach` cleans up

## Mocking Rules

- Mock at system boundaries only (HTTP calls, DB, filesystem, time)
- NEVER mock the code under test
- NEVER mock internal functions of the same module
- Use real implementations where possible (integration > unit for critical paths)
- Warn: mocked tests that pass but prod fails indicates too much mocking

## What Must Be Tested

### Always
- Happy path with valid input
- Each validation error path
- Auth: missing token, expired token, wrong permissions
- Database: connection error, not found, duplicate key
- Concurrent access (if the feature involves shared state)

### Never
- Framework internals (Express routing, ORM query builders)
- Third-party library behavior (trust them to test their own code)
- Implementation details (private functions, internal state)

## Test Files

- Place test files adjacent to source: `user.service.ts` → `user.service.test.ts`
- Or in `__tests__/` directory matching source structure
- Name: `[module].test.[ext]` or `[module].spec.[ext]`
